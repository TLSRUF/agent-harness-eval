\# 21일 계획



하루 3\~4시간 기준. 각 Day의 완료 기준을 만족하면 다음으로 넘어간다.



\## 1주차: 기반과 평가셋

\- Day 1 - 환경과 SDK 확인: 레포 초기화, 구조, 가상환경, README 틀. SDK 문서를 읽고 docs/sdk\_notes.md 정리, 인증 확인. Haiku로 도구 1개 호출 왕복 성공. 완료 기준: 도구를 호출하고 답하며 사용량 필드를 읽어 출력.

\- Day 2 - 도구 구성: 커스텀 도구 3개(폴더 내 텍스트 검색, 파일 요약 통계, 결과 검증용 체크 도구)를 SDK 방식으로 등록. 내장 도구는 허용 목록으로 제어. 경로 탈출 방지 테스트. 완료 기준: pytest 통과, 샌드박스 밖 접근 차단.

\- Day 3 - 호출 래퍼와 로깅: config로 모델, 시스템 프롬프트, 허용 도구, 최대 턴, 도구 설명 버전을 전환. trajectory jsonl 로깅. 완료 기준: 임의 과제 1개를 끝까지 수행하고 로그가 남음.

\- Day 4 - 평가 프레임워크 + 쉬운 과제 15개: 과제 포맷(YAML/JSON), 자동 채점(graders.py). 완료 기준: 15개가 채점 코드와 함께 로드됨. 과제 작성 규칙: 과제 프롬프트에는 도구 이름(search_text, file_stats, check_result, Grep 등)을 쓰지 않고 달성할 목표만 쓴다. 각 과제 정의에 에이전트에게 보이지 않는 분석 전용 필드 overlap_with(같은 일을 할 수 있는 커스텀|내장 도구 쌍, 예: search_text|Grep, file_stats|Read)를 둔다. 비어 있으면 선택률 계산에서 제외한다.

\- Day 5 - 보통 과제 17개: 다단계 과제(여러 파일 조합, 로그 분석, 정제 후 그래프 저장). 완료 기준: 총 32개, 채점 테스트 통과.

\- Day 6 - 어려운 과제 8개 + 채점 검증: 모호한 지시, 충돌하는 문서, 오류가 섞인 입력. 모든 과제의 정답 풀이가 채점을 통과하는지 확인. 완료 기준: 40개 준비 + 검증 통과, 동결은 사용자 손 대조 후.

&#x20; - 동결은 Day 8 베이스라인 시작 전에 반드시 완료한다. 손 대조가 끝나면 사용자가 알린다.

\- Day 7 - 러너: 순차 또는 낮은 동시성 실행, 과제별 임시 폴더, 결과 CSV, 한도 초과 감지와 이어하기, 실행 전 예상 호출 수 출력. 완료 기준: 5개 시험 실행, 중단 후 이어하기 동작.

\- Day 7 메모 (2026-11-05 결정, 구현은 Day 7에):

&#x20; - 큰 캐시 블록 조사: 일부 실행에서 큰 블록(약 33.5k + 41k)이 두 번 만들어져 비용이 약 60% 오른 이유를 로그로 조사한다. 두 블록이 어떻게 다른지 비교한다. 현재 가설(미확정): 계정 커넥터 노출 때문이며, ENABLE_CLAUDEAI_MCP_SERVERS=false 적용 후 2회 실행에서 블록이 사라졌다(표본 2건). 블록 내용을 직접 확인한 것은 아니다.

&#x20; - 한도 처리: 과제 단위 델타는 쓰지 않고 배치 단위(예: 20회) 시작/종료 값으로 측정한다. 한도 초과 감지는 five_hour 절대값 임계 방식으로 설계하고, 임계값은 배치 측정 후 사용자가 정한다.

&#x20; - 측정 배치는 Claude Code 세션이 아니라 터미널에서 직접 실행할 수 있게 CLI 진입점(python -m ...)을 만든다. Claude Code 세션도 같은 구독 한도를 쓰기 때문이다.

&#x20; - 베이스라인 예상 비용은 평균이 아니라 상한으로 잡는다. 커넥터 차단 후 5턴 데모 과제 8회 측정(2026-11-05)에서 건당 최대 $0.0015(긴 휴지 뒤 캐시가 차가웠던 것으로 보이는 1회, 그 외 $0.00077~$0.00082)였다. 따라서 데모급(약 5턴) 과제의 건당 상한은 $0.0015 x 실행 수로 잡는다. 이전 값($0.0165, 커넥터 차단 전 측정)은 폐기한다. 이 상한은 5턴 과제 기준이며 어려운 과제(최대 20턴)에는 적용하지 않는다: 컨텍스트가 누적되어 건당 비용이 더 클 수 있으나 그 크기는 측정 전이라 추정값을 적지 않는다. Day 7의 시험 실행 5개로 난이도별 건당 비용을 측정해 상한을 갱신하고, 비용은 정가 환산 추정치이며 구독 한도 소모와는 별개다.

&#x20; - failure_type 집계: 채점 결과의 failure_type(pass, wrong_value, format_error, missing_output, unexpected_change)을 report.py 집계에 반영하는 일은 Day 7 이후로 미룬다. 현재 report.py는 (subtype, 채점 통과 여부) 5범주만 집계하고, failure_type은 jsonl의 grade 이벤트(graded.failure_type)에 기록만 된다.

&#x20; - 스냅샷과 재채점 완료(2026-11-07): `run_task`가 채점 직후 임시 폴더가 지워지기 전에 outputs와 바뀐 입력 파일을 `results/raw/<로그 줄기>_final/`에 저장하고(파일당 1MB, 실행당 5MB 상한, 초과분은 jsonl의 snapshot 이벤트에 기록), `python -m src.eval.regrade <glob>`가 현재 채점기로 다시 채점한다(모델 호출 없음). **Day 7 러너는 `run_task(..., outputs=task.outputs)`로 호출해야** 스냅샷에 출력 파일이 담긴다. report.py에는 pass^k, 일관성, 도구 오류율(커스텀/내장 구분), min_steps 구간별 성공률도 추가됐다.



\## 2주차: 베이스라인과 실험 A\~C

\- Day 8 - 베이스라인: 기본 설정(Haiku 5.5, 기본 도구 설명, 검증 없음, 최대 턴 20)으로 40개 x 3회. report.py로 성공률, 평균 턴, 도구 오류율, 비용 추정치, 난이도별 성공률. 한도가 모자라면 나눠서 실행. 완료 기준: 베이스라인 표 저장.

\- Day 9 - 실험 A 구현: 도구 설명 버전 2종(짧게/자세히+예시)을 config로 전환. 완료 기준: 설정만 바꿔 두 버전 실행. 실험 A의 질문: 도구 설명 길이(짧게/자세히)에 따라 (a) 성공률 (b) 커스텀 도구 선택률 (c) 도구 오류율이 어떻게 변하는가. 성공률은 내장 도구로도 풀리는 과제가 많아 거의 변하지 않을 수 있으며, 선택률이 주된 관찰 지표다. 모든 결과는 표본 크기(N개 과제, 과제당 M회)와 함께 보고한다.

\- Day 10 - 실험 A 실행과 분석: 40개 x 2회, 베이스라인 대비 표와 해석 3줄. 완료 기준: results/expA 저장. 해석은 Day 9에 적은 (a)(b)(c) 정의를 따르고, 성공률과 선택률은 별도 열로 보고한다(합치지 않음).

\- Day 11 - 실험 B 구현: 시스템 프롬프트에 "답하기 전에 결과를 검증하고 필요하면 수정하라" 단계를 추가(토글). 완료 기준: 토글 동작.

\- Day 12 - 실험 B 실행과 분석: 성공률 변화와 비용 증가율 비교. 완료 기준: results/expB 저장.

\- Day 13 - 실험 C: 최대 턴 5 / 20 비교(여유가 있으면 10도). 턴 제한에 걸려 실패한 비율 기록. 완료 기준: results/expC 저장. max_turns 값은 Day 8 베이스라인의 num_turns 분포(중앙값, 상위 10%)를 보고 정한다.

\- Day 14 - 예비일: 밀린 작업, 사용량 한도 대기, 이상 결과 재확인, 채점기 점검. 완료 기준: 지금까지 결과 재현 가능.



\## 3주차: 모델 비교, 분석, 정리

\- Day 15 - 실험 D: Haiku 전체 결과 vs Sonnet 5.5 부분 실행(기본 40개 x 1회, 부족하면 어려운 과제 8개와 보통 과제 일부). 같은 과제 집합끼리만 비교. 완료 기준: 비교표와 "비용 대비 성공률" 그래프 초안, 비교 범위 명시.

\- Day 16 - 실패 분석: 유형 분류(도구 선택 오류, 인자 오류, 반복 루프, 조기 종료, 환각, 채점 불일치), 유형별 건수 표와 대표 사례 3개. 완료 기준: docs/failure\_analysis.md.

\- Day 17 - 개선 실험: 가장 많은 실패 유형 하나를 골라 개선(시스템 프롬프트, 도구 오류 메시지 등), 전후 비교. 완료 기준: 전후 점수 표.

\- Day 18 - 최종 실행과 시각화: 최적 설정으로 Haiku 40개 x 3회. 그래프: 실험별 성공률, 비용 대비 성공률, 난이도별 성공률. 완료 기준: results/final, 그래프 저장.

\- Day 19 - README: 맨 위 3줄(문제 -> 접근 -> 결과 수치), 주 실험 모델은 Haiku 5.5이고 Sonnet 5.5는 비교용 부분 실행임을 명시, 구조, 실행 방법(claude login 또는 API 키), 결과 표, 실패 분석 요약, 한계. 완료 기준: README만으로 재현 가능.

\- Day 20 - 마무리: 데모 영상 또는 GIF, 코드 정리, 테스트, 라이선스, 비밀 정보 점검. 완료 기준: 깨끗한 클론에서 설치 후 샘플 과제 실행.

\- Day 21 - 예비일과 홍보: 못 끝낸 작업, 블로그 글 초안, 이력서용 bullet 3개.
