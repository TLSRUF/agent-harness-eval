# 과제 설계 (Day 4)

평가셋 40개(쉬움 15 / 보통 17 / 어려움 8) 중 쉬운 과제 E01~E15를 만든 시점의 설계 기록이다. 보통(M)·어려움(H) 과제는 Day 5~6에 같은 규칙으로 추가하고 Day 6에 동결한다. 채점 기준의 자동 생성 목록은 `docs/task_grading_criteria.md`를 본다.

## 1. 과제 ID와 파일 구성
- ID: 난이도 글자 + 두 자리 번호. `E01`~`E15`(쉬움), `M01`~`M17`(보통), `H01`~`H08`(어려움). 한 번 쓴 ID는 재사용하지 않는다.
- 과제마다 `rev`(수정 번호)를 둔다. 동결(Day 6) 전에 고치면 ID는 그대로 두고 `rev`만 올린다.
- 파일: `src/eval/tasks/<ID>.json`(정의), `fixtures/<ID>/`(초기 파일), `src/eval/solutions/<ID>.py`(정답 풀이 `solve(workdir)`), 채점은 내장 채점기(`graders.py`) 또는 `graders_user.py`의 `grade_<ID>`.
- 동결 방식(Day 6 예정, **아직 `MANIFEST.json`은 만들지 않았다**): 과제 JSON, fixture, 채점 설정의 sha256을 기록하고 테스트가 변경을 잡는다. `.gitattributes`에서 `fixtures/**`를 `-text`로 두어 Windows 줄바꿈 변환이 해시를 바꾸지 않게 했다.

## 3. 프롬프트 규칙
- 한국어로 통일한다(40개 전체). 출력 형식 문자열은 글자 그대로 둔다. fixture 안의 로그·설정 내용은 영어여도 된다.
- 도구 이름(`search_text`, `file_stats`, `check_result`, `Grep`, `Glob`, `Bash`, 대문자 `Read`/`Write`/`Edit`, `mcp__`)을 쓰지 않는다. 로더가 검사하며 한국어 조사가 붙은 경우(`Grep을`)도 잡는다(ASCII 경계 기준).
- 출력 파일을 만드는 과제는 `format_hint`가 필수이고, 프롬프트에 글자 그대로 들어 있어야 한다. 정답이 새지 않도록 값 자리는 `<숫자>`, `<파일명>`처럼 자리표시자로 쓴다. 형식이 모호한 과제는 만들지 않는다.
- `overlap_with`는 에이전트에게 전달되지 않는 분석 전용 필드다.

## 4. overlap_with 기준
- **문자열 검색이 과제의 핵심 동작이면 `search_text|Grep`을 넣는다.** 파일의 줄/단어/크기 통계가 핵심이면 `file_stats|Read`를 넣는다. 둘 다 아니면 비운다(선택률 계산에서 제외).
- 현재 15개 중 6개: `search_text|Grep` 4개(E01, E02, E08, E13), `file_stats|Read` 2개(E03, E10). 40개 전체에서 15~20개가 되도록 Day 5~6에서 늘린다.
- 관찰(표본 1회, 일반화 금지): E13을 에이전트가 Grep이 아니라 Read로 파일 전체를 읽고 풀었다. `Read`는 `search_text|Grep` 쌍에 없으므로 이 실행은 선택률 쌍에서 "둘 다 아님"으로 집계된다.

## 5. 채점
- 내장 채점기 3종: `text_file`(출력 파일 내용 비교), `edit_file`(한 줄만 바꾸기), `number_file`(숫자 허용 오차). 사용자 지정 채점기는 `custom:grade_<ID>`.
- 공통 관대 기준(겉모양만): 앞뒤 공백, 끝 줄바꿈, 연속 공백, CRLF/LF 차이. 내용(숫자, 파일명, 대소문자, 줄 순서, 문장부호)은 엄격하다. E13은 이보다 더 엄격하다(끝 줄바꿈 하나와 `\r\n`/`\n` 차이만 허용). E14는 제품 이름의 대소문자를 무시한다(`grading.loose`에 선언).
- 결과는 `{"passed", "failure_type", "reason"}`이고 failure_type은 `pass`, `wrong_value`(값이 틀림), `format_error`(값은 맞고 형식만 틀림), `missing_output`(출력 없음 또는 비어 있음), `unexpected_change`(건드리면 안 되는 입력이 바뀜) 중 하나다. 판정 순서는 missing_output, unexpected_change, 내용 비교다. `format_error`는 통과가 아니다.

## 6. 정답 풀이와 채점기의 독립 검증
1. **서로 다른 경로로 만든 두 개의 정답**: 정답 풀이는 fixture를 읽어 코드로 답을 계산하고, 채점 기대값은 과제 JSON에 사람이 손으로 센 값(`hand_check`에 근거)으로 따로 적는다. 둘이 어긋나면 풀이가 채점을 통과하지 못한다.
2. **무작업 대조**: 아무것도 하지 않은 fixture는 채점에서 실패해야 한다(항상 통과하는 채점기를 거른다).
3. **채점 경로별 단위 테스트**: 채점기마다 모든 failure_type 경로에 변형 답(공백 변형, 값만 있는 답, 값이 틀린 답, 파일 없음, 입력 변경 등)을 넣어 기대 분류와 같은지 확인한다.
4. **fixture 약속의 코드 검증**: 줄 수, 특정 값의 위치와 개수(WARN 줄 번호, Cat 위치, qty 최댓값의 유일성), 함정 단어가 없음을 테스트가 센다.
5. **사람의 직접 대조**: E01~E12의 프롬프트, fixture 요약, 정답, 손으로 센 근거를 표로 제공했다. 사용자의 대조 완료 여부는 이 문서 작성 시점에 확인되지 않았다(동결 전 확인 필요).
6. 로더 `python -m src.eval.loader --check`가 위 1, 2와 도구 이름 금지, overlap 형식, 필수 파일 존재를 과제마다 검사한다.
- 한계: 3, 4의 변형 답은 합성한 것이다. 실제 에이전트 출력으로 채점기를 확인한 것은 Haiku 3건(E01, E11, E13)뿐이다.

## 7. 한계
- **프롬프트 언어(한국어) 통일은 결과에 영향을 줄 수 있다.** 같은 과제를 영어로 쓰면 성공률과 도구 선택이 달라질 수 있으며 이는 검증하지 않았다.
- 에이전트에 코드 실행 도구가 없어 계산이 필요한 과제는 숫자를 작게 유지했고, 그만큼 쉬운 과제의 성공률이 높게 나올 수 있다(천장 효과 가능성은 Day 8 베이스라인에서 확인).
- Windows에서 정답 풀이 E01~E12는 줄바꿈 변환(`\n`→`\r\n`)이 일어나는 `write_text`를 쓴다. 채점기가 CRLF를 정규화하므로 통과에는 영향이 없지만, 해시나 바이트 비교를 하는 곳에서는 주의가 필요하다.
