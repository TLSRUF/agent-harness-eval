# 면접 노트 (agent-harness-eval)

이 문서는 프로젝트에 대해 받을 만한 질문 15개와 답의 뼈대다. 수치와 판단은 [results.md](results.md), [failure_analysis.md](failure_analysis.md), [progress.md](progress.md)에서 가져왔고, 새로 만든 주장은 없다. 모든 비율에는 표본 크기를 붙였고, 근거가 없는 부분은 "확인 불가"나 "가설"로 적었다. 14번은 본인의 경험을 직접 써야 하는 자리라 비워 두었다.

## 1. 이 프로젝트는 무엇이고 왜 만들었나?

Claude Agent SDK로 도구를 쓰는 에이전트를 만들고, 같은 모델이라도 하네스 설정(도구 설명, 검증 지시, 최대 턴 수, 모델)에 따라 채점 통과율과 비용이 얼마나 달라지는지 재는 실험 프로젝트다. 평가셋은 과제 40개(쉬움 15, 보통 17, 어려움 8)이고 설정을 하나씩만 바꿔 실험 A~F를 돌렸다. 핵심 질문은 "모델을 바꾸지 않고 하네스만 바꿔도 결과가 달라지는가"다.

## 2. 왜 주 모델이 Haiku이고 Sonnet은 부분 실행뿐인가?

구독 사용량 한도가 작아 큰 실행을 나눠 돌려야 했다. 프로젝트 규칙은 모든 실험의 기본 에이전트 모델을 Haiku로 두는 것이고(모델명은 config로 분리), Sonnet은 실험 D(모델 비교)에서만 같은 40개 과제 x 1회(총 40건)로 돌렸다. 평균 비용은 Haiku $0.0015 대 Sonnet $0.0139이고 비용 합 비율은 9.2배(과제 40개, 건당 1회)다. 이 비용은 로그의 추정치이며 구독 한도 소모와의 관계는 확인 불가다.

## 3. 평가셋을 왜 동결했고, 어떻게 보장했나?

같은 시험으로 비교해야 설정 변경의 효과를 분리할 수 있어서다. 과제 JSON 40개, fixture, 채점 파일, 정답 풀이, 도구 정의 v1, 설정 기본값의 sha256을 MANIFEST.json에 고정했고(2026-11-09, 정답을 사람이 직접 대조한 뒤), 바뀌면 테스트가 실패한다. 버그를 발견하면 고치기 전에 알리고, 승인된 변경만 반영한 뒤 다시 동결하고 사유를 progress.md에 적는 규칙이다. 모든 과제에는 정답 풀이가 채점을 통과해야 한다는 조건도 있다.

## 4. 베이스라인 결과는 어땠고, 천장 효과는 어떻게 다뤘나?

베이스라인(default) 채점 통과율은 100% (120/120)(N=40, 과제당 3회)였다. 90% 이상이면 천장 효과가 생기므로 설정 간 통과율 차이를 가리기 어렵다고 알리고, 통과율만 보지 않고 도구 선택률, 사용률, 정상 종료율, 비용 같은 다른 지표를 함께 봤다. 실험 D의 haiku 100% (40/40), sonnet 100% (40/40)도 같은 이유로 모델 간 정확도 차이를 말할 수 없다(가설: 천장 효과).

## 5. 실험을 왜 한 번에 변수 하나만 바꿨나?

두 개를 동시에 바꾸면 어느 쪽이 결과를 만들었는지 분리할 수 없어서다. 그럼에도 한계가 있다. 실험 A는 도구 3개(search_text, file_stats, check_result)의 설명을 동시에 바꿔서 효과를 도구별로 나누지 못했다. 이 한계는 README와 results.md에 적었다. 또 실험 전에 예측을 적어 두고 결과와 대조했는데(progress.md의 "사용자 예측 기록"), 예를 들어 Day 7의 비용과 턴 수 예측은 둘 다 틀렸다. 예측이 틀린 것도 기록으로 남겼다.

## 6. 실험 A(도구 설명)에서 무엇을 발견했고, 얼마나 확신하나?

file_stats 선택률이 default 62% (15/24)에서 long 100% (24/24)로 올랐다(N=8, 과제당 3회, 총 24건, 30건 미만). search_text 선택률은 default 0% (0/36)에서 long_directive 28% (10/36)였다(N=12, 총 36건). 가설: 쓰임새를 적으면 도구 선택이 늘어난다. 채점 통과율은 네 설정 모두 95~100%(각 N=40, 120건)여서 선택률 증가가 통과율을 올리는지는 확인 불가다. 반복이 3회뿐이라 우연 범위도 크다.

## 7. 실험 B에서 check_result 사용률이 늘었는데, 검증이 잘 됐다는 뜻인가?

아니다. check_result 사용률은 default 50% (60/120)에서 verify 90% (108/120), verify_tool 93% (112/120)로 늘었다(N=40, 총 120건). 그러나 check_result는 파일 존재, 포함 문자열, 최소 줄 수만 확인하고 값의 정확성은 확인하지 않는다. 그래서 검증 행동이 늘었다는 관찰일 뿐 정확성이 늘었다는 근거가 아니다. 늘어난 검증이 값 오류를 줄이는지는 확인 불가다.

## 8. 실험 C에서 정상 종료율과 채점 통과율이 크게 다른 이유는?

max_turns 3에서 정상 종료율은 34% (41/120)인데 채점 통과율은 93% (112/120)다(N=40, 총 120건). max_turns에 걸려 error_max_turns로 끝났어도 그 전에 결과 파일을 써 놓은 실행이 많았고, 채점은 실행이 끝난 시점의 파일 상태로 하기 때문이다. 그래서 두 지표를 함께 봐야 한다. 규칙은 error_max_turns를 설정 한계로 인한 결과로 인정하고 다시 돌리지 않는 것이며, error_max_turns인데 통과한 실행은 따로 센다(max_turns 3, 4, 5에서 71/79, 29/34, 8/9).

## 9. 실험 C 해석에서 스스로 바로잡은 것은 무엇인가?

처음에는 "한계에서 잘린 실행의 대부분은 마무리 응답에서 잘렸다"는 식으로 적었다. 로그를 다시 계산하니 error_max_turns인데 통과한 108건(3: 71, 4: 29, 5: 8)이 모두 결과 파일 쓰기가 성공한 뒤에 잘렸고, 48건(44, 3, 1)은 쓰기 직후, 60건(27, 26, 7)은 쓰기 뒤 도구가 한 번 더 호출됐다(대부분 check_result). 마무리 응답에서 잘렸다는 직접 증거는 없어서 가설로 낮췄고, 이 수치는 results_summary.py가 로그에서 계산하고 테스트가 고정한다.

## 10. 실험 D에서 Sonnet이 낫다고 말할 수 있나?

말할 수 없다. 같은 40개 과제 x 1회(총 40건)에서 채점 통과율이 haiku 100% (40/40), sonnet 100% (40/40)로 같아 천장 효과로 모델 간 차이를 가린다(가설). 말할 수 있는 것은 비용뿐이다: 평균 $0.0015 대 $0.0139, 비용 합 비율 9.2배(과제 40개, 과제별 비율 중앙값 11.0). 과제당 1회뿐이라 반복 사이 변동은 확인 불가다.

## 11. 실험 E의 H01 짝 맞춤 오류는 무엇이고, 왜 결론을 확정하지 않았나?

file_stats 출력에 파일 이름이 없어서 파일 여러 개를 병렬로 호출하면 호출과 결과의 짝을 순서로만 맞춰야 하고, H01에서 이 짝 오류가 관찰됐다(도구 출력은 정확했음). 출력에 파일 이름을 붙인 expE는 3/3인데, 같은 날 연달아 돌린 대조군 expEctl도 1/3이었다(H01 한 과제 x 3회, 각 3건, 30건 미만). 3일 전의 expA long은 0/3이었다. 대조군도 한 번 통과했고 표본이 작아 효과는 가설 수준이다. 도구 정의 v1은 동결이라 고치지 않았다.

## 12. 실험 F는 왜 효과를 확인하지 못했나?

search_text 출력 맨 앞에 전체 일치 줄 수를 붙였을 때 expFctl 18/20, expF 19/20이었다(N=4, 과제당 5회, 총 20건, 30건 미만). 변형이 닿은 실행, 즉 search_text를 쓴 실행이 조건당 5/20뿐이라 효과를 볼 표본이 없었다. 실패 3건은 모두 도구 출력에 정답이 있었는데 에이전트가 직접 세다 틀린 경우였고, 새로 붙인 일치 개수 줄을 받은 실행은 없었다. 효과 확인에는 search_text 사용 실행을 늘려야 한다.

## 13. 채점기의 버그는 어떻게 찾았나?

과제마다 정답 풀이가 채점을 통과해야 한다는 규칙을 두고, 채점 부품을 단위 테스트했다. 그 과정에서 프롬프트 검사와 값 판별이 한국어 조사를 못 다루는 문제, 소수의 일부를 다른 값으로 오인하는 문제 등 버그 3건이 나왔다. 첫 에이전트 실행은 12/12 통과였고, 에이전트 실행에서 채점기 버그가 드러나지는 않았다. 예측은 "정답 풀이 1~2개가 채점기 버그로 실패"였으니 형식은 틀리고 취지(채점기에 버그가 있다)는 맞은 셈이다.
